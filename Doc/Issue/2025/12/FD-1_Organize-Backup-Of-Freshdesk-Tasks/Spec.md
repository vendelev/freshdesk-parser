# Спецификация: Организация бекапа списка задач из Freshdesk

## Описание проблемы/потребности

Требуется создать функциональность для регулярного резервного копирования списка всех задач из Freshdesk. Это необходимо для:
- Защиты от потери данных при недоступности Freshdesk API
- Обеспечения автономного анализа и отчетности по задачам
- Создания полного снимка состояния всех задач на определенный момент времени
- Подготовки данных для дальнейшей обработки и импорта в другие системы

---

## Функциональные требования

### FR1. Получение данных из Freshdesk API

- **FR1.1**: Система должна подключаться к Freshdesk API на основе учетных данных (API ключ)
- **FR1.2**: Система должна получать полный список всех задач (tickets) независимо от их статуса
- **FR1.3**: Система должна получать все доступные поля каждой задачи согласно API Freshdesk
- **FR1.4**: Система должна корректно обрабатывать пагинацию при получении больших объемов данных

### FR2. Сохранение бекапа

- **FR2.1**: Система должна сохранять полученные данные в файловую систему
- **FR2.2**: Бекап должен храниться в формате JSON
- **FR2.3**: Каждый бекап должен содержать полный снимок всех задач в момент создания
- **FR2.4**: Предыдущий бекап должен быть заменен новым при выполнении операции бекапа
- **FR2.5**: Файл бекапа должен содержать метаданные: дату/время создания, количество задач

### FR3. Инициирование бекапа

- **FR3.1**: Бекап должен быть доступен через консольную команду Laravel
- **FR3.2**: Система должна предоставить команду `php artisan backup:tickets` для инициирования бекапа
- **FR3.3**: Команда должна выводить статус выполнения операции и метаинформацию о созданном бекапе
- **FR3.4**: Команда должна поддерживать флаг `--help` с описанием синтаксиса

### FR4. Обработка ошибок

- **FR4.1**: При недоступности Freshdesk API система должна возвращать информативную ошибку
- **FR4.2**: При ошибках записи на диск система должна откатывать операцию и сохранять предыдущий бекап
- **FR4.3**: Система должна логировать все ошибки для диагностики

---

## Нефункциональные требования

### NFR1. Производительность

- **NFR1.1**: Бекап задач должен завершаться в разумное время (не более 100 минут для стандартного количества задач)
- **NFR1.2**: Система должна корректно обрабатывать Freshdesk API rate limits

### NFR2. Надежность

- **NFR2.1**: Система должна корректно обрабатывать потери соединения с Freshdesk API
- **NFR2.2**: При невозможности завершить бекап, система должна сохранять предыдущий бекап в целостности

### NFR3. Безопасность

- **NFR3.1**: API ключ Freshdesk должен храниться в переменных окружения (.env файл)
- **NFR3.2**: API ключ не должен логироваться или попадать в статус-отчеты
- **NFR3.3**: Бекап должен содержать только те данные, которые доступны через API с текущим уровнем доступа

### NFR4. Масштабируемость

- **NFR4.1**: Система должна корректно обрабатывать растущее количество задач
- **NFR4.2**: Файловая система должна справляться с размерами бекапов (предполагаемый размер JSON для 1000 задач ~ 50-100 МБ)

### NFR5. Удобство использования

- **NFR5.1**: Процесс инициирования бекапа должен быть простым и понятным (одна команда)
- **NFR5.2**: Команда должна выводить понятные сообщения об ошибках и статус выполнения
- **NFR5.3**: Команда должна поддерживать флаг `--help` с описанием синтаксиса команды

## Модель предметной области

### Entity и Value Objects

**Ticket (Задача)**
- `id`: int — уникальный идентификатор в Freshdesk
- `subject`: string — название/тема задачи
- `description`: string — описание задачи
- `status`: string — статус (open, pending, resolved, closed и т.д.)
- `priority`: int — приоритет (1-4)
- `requester_id`: int — ID автора задачи
- `assigned_to_id`: int | null — ID назначенного сотрудника
- `group_id`: int | null — ID группы
- `created_at`: datetime — дата создания
- `updated_at`: datetime — дата последнего обновления
- `due_date`: datetime | null — дата дедлайна
- `tags`: array — список тегов
- `custom_fields`: array — пользовательские поля
- (и другие поля согласно API Freshdesk)

**Backup (Бекап)**
- `id`: string — уникальный идентификатор бекапа (например, timestamp)
- `created_at`: datetime — дата/время создания бекапа
- `total_tickets`: int — количество сохраненных задач
- `file_path`: string — путь к файлу бекапа
- `status`: string — статус бекапа (pending|completed|failed)
- `error_message`: string | null — сообщение об ошибке при сбое

## Сценарии использования

### Use Case 1: Выполнение бекапа всех задач

**Актор**: Разработчик/администратор (в консоли)

**Основной сценарий**:
1. Пользователь выполняет команду `php artisan backup:tickets`
2. Система инициирует процесс получения всех задач из Freshdesk API
3. Система получает полный список задач с обработкой пагинации
4. Система сохраняет данные в JSON файл в выбранной директории
5. Система выводит в консоль информацию о созданном бекапе (кол-во задач, время создания, путь к файлу, статус SUCCESS)

**Альтернативный сценарий 1: Ошибка подключения к Freshdesk**:
- Система не может подключиться к Freshdesk API
- Система выводит ошибку в консоль с описанием проблемы
- Предыдущий бекап остается нетронутым
- Команда завершается с exit code 1

**Альтернативный сценарий 2: Ошибка записи на диск**:
- Система не может записать файл на диск
- Система откатывает операцию и сохраняет предыдущий бекап
- Система выводит ошибку в консоль
- Команда завершается с exit code 1

### Use Case 2: Получение справки по команде

**Актор**: Разработчик/администратор (в консоли)

**Основной сценарий**:
1. Пользователь выполняет команду `php artisan backup:tickets --help`
2. Система выводит справку по команде, включая описание синтаксиса

## Риски

### R1: Rate limiting Freshdesk API

**Описание**: Freshdesk API имеет ограничение на количество запросов. При большом количестве задач можно превысить лимит.

**Влияние**: Бекап не будет завершен.

**Вероятность**: Средняя

**Смягчение**: Реализовать экспоненциальный retry с backoff, соблюдать Rate-Limit headers

### R2: Размер файла бекапа

**Описание**: При большом количестве задач файл бекапа может быть очень большим и занимать много места на диске.

**Влияние**: Проблемы с дисковым пространством.

**Вероятность**: Средняя

**Смягчение**: Мониторить размер файлов, рассмотреть сжатие (gzip)

### R3: Изменение структуры API Freshdesk

**Описание**: Freshdesk может изменить структуру API или убрать некоторые поля.

**Влияние**: Бекап может содержать неправильные или неполные данные.

**Вероятность**: Низкая

**Смягчение**: Поддерживать версионирование API, регулярно проверять совместимость

### R4: Недостаток прав доступа

**Описание**: API ключ может иметь недостаточные права для получения всех задач.

**Влияние**: Бекап будет содержать неполные данные.

**Вероятность**: Низкая

**Смягчение**: Четко документировать требуемые права, проверять на начальном этапе

## Критерии приемки

### CA1: Успешное получение всех задач

- [ ] При выполнении бекапа система получает все задачи из Freshdesk (полный список, независимо от статуса)
- [ ] Количество задач в бекапе совпадает с количеством задач в Freshdesk API

### CA2: Корректное сохранение данных

- [ ] Бекап сохраняется в файловую систему в формате JSON
- [ ] Все поля задачи полностью присутствуют в бекапе
- [ ] Бекап содержит метаданные (дата создания, количество задач)

### CA3: Консольная команда

- [ ] Команда `php artisan backup:tickets` доступна и выполняется без ошибок
- [ ] Команда завершается с exit code 0 при успехе
- [ ] Команда выводит информацию о созданном бекапе (кол-во задач, время создания, путь к файлу)

### CA4: Обработка ошибок

- [ ] При недоступности Freshdesk система выводит понятное сообщение об ошибке
- [ ] Команда завершается с exit code 1 при ошибке
- [ ] При ошибке записи на диск система откатывает операцию

### CA5: Безопасность

- [ ] API ключ хранится в переменных окружения
- [ ] API ключ не попадает в логи или вывод команды

### CA6: Справка команды

- [ ] Команда поддерживает флаг `--help`
- [ ] Флаг `--help` выводит описание синтаксиса команды

## Не входит в реализацию

- **История версий бекапов**: Система сохраняет только последний бекап, история не требуется.
- **Поддержка других форматов**: Бекап сохраняется только в JSON.
- **Автоматическое выполнение по расписанию**: Бекап выполняется только по команде (может быть добавлено в cron позже).
- **REST API**: Интеграция реализуется только через консольную команду, HTTP endpoints не требуются.
- **Синхронизация изменений в реальном времени**: Система создает полный снимок, не отслеживает инкрементальные изменения.
- **Восстановление данных из бекапа**: В текущей версии бекап — только для хранения, восстановление не требуется.
- **Шифрование бекапа**: Данные сохраняются в открытом виде (предполагается защита на уровне файловой системы).
- **Интеграция с облачными хранилищами**: Бекап хранится только в локальной файловой системе.
