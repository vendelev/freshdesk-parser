OpenSpec спецификацию ведут как единый «живой» документ — источник истины, который обновляется через промежуточные изменения (дельты), а не пишется с нуля каждый раз.

## Основная структура

OpenSpec создаёт в проекте папку openspec/ со следующей структурой:

```text
openspec/
├── specs/          # Текущая спецификация (источник истины)
│   └── auth/
│       └── spec.md
├── changes/        # Активные изменения (дельты)
│   └── add-2fa/
│       ├── proposal.md
│       ├── tasks.md
│       └── specs/
│           └── auth/
│               └── spec.md
└── project.md      # Общие соглашения проекта
```

* specs/ — текущее состояние системы, «единственный источник истины».
* changes/ — папка с предложениями изменений, где каждое изменение живёт в своей папке.

## Как правильно вести спецификацию

### 1. Начинайте с openspec init

Инициализируйте OpenSpec в проекте:

```shell
cd my-project
openspec init
```

Это создаст папку openspec/, настроит интеграцию с вашим AI-ассистентом (Cursor, Claude Code и др.) и добавит AGENTS.md.

### 2. Пишите спецификацию в specs/

В openspec/specs/ хранится текущая, актуальная спецификация системы.

* Разбивайте спецификацию по темам: auth/spec.md, billing/spec.md, api/spec.md и т.д..
* Каждый файл — это Markdown-документ с требованиями, сценариями и примерами.

Пример структуры specs/auth/spec.md:

```markdown
# Auth Specification

## Purpose
Аутентификация и управление сессиями.

## Requirements

### Requirement: User Authentication
Система ДОЛЖНА выдавать JWT при успешном входе.

#### Scenario: Valid credentials
- WHEN пользователь вводит корректные учётные данные
- THEN возвращается JWT

### Requirement: Password Reset
Система ДОЛЖНА позволять сбросить пароль по email.

#### Scenario: Reset link sent
- WHEN пользователь запрашивает сброс пароля
- THEN на email отправляется ссылка со сроком действия 1 час

```

### 3. Вносите изменения через changes/

Когда нужно что‑то изменить, не правьте specs/ напрямую, а создайте change proposal:

```shell
# Или через команду в AI-ассистенте, например:
/openspec:proposal Add profile search filters
```

AI создаст папку в changes/add-profile-filters/ с файлами:

* proposal.md — зачем и что меняем.
* tasks.md — пошаговый план реализации.
* specs/auth/spec.md — дельта (изменения к основной спецификации).

Пример дельты (changes/add-profile-filters/specs/auth/spec.md):

```markdown
# Delta for Auth

## ADDED Requirements

### Requirement: Profile Search Filters
Система ДОЛЖНА позволять фильтровать профили по роли и команде.

#### Scenario: Filter by role
- WHEN пользователь выбирает роль "Developer"
- THEN в результатах показываются только профили с ролью "Developer"

## MODIFIED Requirements

### Requirement: User Authentication
Система ДОЛЖНА выдавать JWT при успешном входе и сохранять роль в токене.

```

### 4. Согласовывайте спецификацию

Перед реализацией:

* Просматривайте дельту: openspec show add-profile-filters.
* Уточняйте требования, сценарии, примеры, пока не будет полного согласия с AI и командой.
* Добавляйте acceptance criteria, edge cases, ограничения (например, «фильтр по команде работает только для админов»).

### 5. Реализуйте по спецификации

Когда спецификация согласована:

```shell
# Или через команду:
/openspec:apply add-profile-filters
```

AI будет генерировать код, строго следуя вашей спецификации из changes/.

### 6. Архивируйте и обновите specs/

После реализации:

```shell
# Или через команду:
/openspec:archive add-profile-filters
```

OpenSpec:

* Перенесёт изменения из changes/add-profile-filters/specs/ в specs/.
* Удалит папку changes/add-profile-filters/ (или переместит в архив).
* Обновит источник истины, чтобы он отражал текущее состояние системы.

## Лучшие практики

1. Делайте спецификацию «живой»
  - Всегда обновляйте specs/ через archive, а не вручную.
  - Спецификация в specs/ должна быть актуальной — как документ, по которому можно понять, что делает система прямо сейчас.
2. Пишите чёткие требования
  - Используйте ДОЛЖНА / MUST, СЛЕДУЕТ / SHOULD для указания обязательности. 
  - Каждое требование — с хотя бы одним сценарием (WHEN/THEN).
  - Добавляйте примеры: тела запросов, ответов, ошибок, граничных значений.

3. Разбивайте по темам
  - Не храните всё в одном файле.
  - Разделяйте спецификацию по модулям: auth/, billing/, api/, ui/ и т.д..
  - В project.md опишите общие соглашения: стек, архитектура, стиль кода, подходы к ошибкам и логированию.

4. Используйте дельты для изменений
  - Любое изменение — через changes/, а не прямое редактирование specs/.
  - Это даёт чёткую историю изменений, понятные diff’ы и возможность откатить/проверить, что именно поменялось.

5. Интегрируйте в процесс команды
  - Настройте OpenSpec на всех участников (AI-ассистенты, IDE).
  - Начинайте с новых фич, потом постепенно переносите в спецификацию старые части системы (brownfield).
  - Проводите ревью не только кода, но и спецификации перед реализацией.
